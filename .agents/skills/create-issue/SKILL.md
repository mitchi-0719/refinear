# Create Issue

曖昧な依頼を、重複のない実行可能なIssueへ変換し、作成したIssueのURLを返す。

## 最初に確認モードを決める

ユーザーが「確認しながら」「原稿を見てから」などと指定した場合は確認あり、「確認なしで」「そのまま作って」などと指定した場合は確認なしとして、その指定を聞き直さない。確認方法が指定されていない場合だけ、スキルを開始した最初のユーザー向け応答で次を確認してターンを終了する。

> Issueの情報が不足している場合、確認しながら進めますか？

回答後は、次のどちらか一方で最後まで進める。

### 確認あり

- リポジトリから判明しない情報のうち、Issueの目的、範囲、完了条件を左右するものだけを質問する。
- 関連する質問はまとめ、回答済みの内容を聞き直さない。
- 情報が揃ったら、起票前にタイトル、本文、assignee、重複候補の扱いをそのまま提示し、ユーザーの明示的な承認を待つ。
- 修正指示があれば原稿だけを直し、再承認を待つ。承認前にIssueを作成しない。

### 確認なし

- 最初の回答後は追加質問や原稿承認を求めない。
- リポジトリと依頼から安全に推測できる内容だけを補い、推測できない内容は本文の`未確定事項`へ明記する。
- 重複検索と原稿作成が完了したら、そのままIssueを起票する。
- 不明点を埋めるために要件、技術選定、完了条件を創作しない。

## リポジトリとアクセス経路を確認する

1. `git remote -v`から対象GitHubリポジトリを特定する。特定できない場合は、確認ありではユーザーへ聞き、確認なしでは起票せず完成原稿を返す。
2. `AGENTS.md`、`.github/ISSUE_TEMPLATE/`、依頼に関係するドキュメントとコードを読み取り専用で確認する。
3. GitHub操作の前に`docs/GITHUB_AUTHENTICATION.md`を読み、GitHub Appを優先し、定義された条件を満たす場合だけ`gh`へフォールバックする。
4. 利用可能な経路で必要な操作ができなければ、Issueを作成したふりをせず、完成原稿、失敗した経路、実エラー、必要なユーザー対応を返す。

このスキルではリポジトリ内のファイル編集、branch作成、stage、commit、push、PR作成を行わない。

## 重複Issueを検索する

原稿を確定する前に、openとclosedのIssueを両方検索する。

1. 依頼の対象機能、ユーザー操作、現象、期待結果から検索語を複数選ぶ。
2. タイトルだけでなく本文も対象にし、単一の検索語だけで該当なしと判断しない。
3. 候補のタイトル、本文、状態、コメント、完了条件を読み、語句の一致ではなく目的と期待結果が同じかで判断する。
4. 判定結果を次のように扱う。
   - 明確に同じopen Issueがある: 新規作成せず、そのIssueの番号、タイトル、URL、一致理由を返して終了する。
   - 類似するopen Issueしかない: 確認ありでは、既存Issueを使うか新規作成するかユーザーに確認する。確認なしでは新規Issueを作り、`関連Issue`に候補を記載する。
   - 明確に同じclosed Issueがある: 確認ありでは、reopenするか新規Issueを作るか確認する。確認なしでは新規Issueを作り、closed Issueと過去対応済みであることを`関連Issue`に記載する。
5. 重複検索そのものを実行できない場合は、重複作成を避けるため起票しない。確認モードにかかわらず、完成原稿と検索できなかった理由を返す。

## Issue原稿を作る

通常は`.github/ISSUE_TEMPLATE/feature.md`の本文を基にする。frontmatterのプレースホルダーを本文へ含めない。要望の種類に応じて、タイトル接頭辞を使い分ける。

- 新機能・挙動追加: `feat:`
- 不具合修正: `fix:`
- ドキュメント: `docs:`
- 開発環境・運用・保守: `chore:`

本文はテンプレートの意図を保ち、少なくとも依頼内容と検証可能な完了条件を含める。

```markdown
## やりたいこと

- 何を、なぜ必要としているか

## ✅ 完了条件 (Acceptance Criteria)

- [ ] 利用者または開発者が確認できる結果
```

必要な場合だけ、次の見出しを追加する。

- 不具合: `現象`、`再現手順`、`期待する結果`
- 背景情報: `背景・目的`
- 既存Issue候補: `関連Issue`
- 確認なしモードで残る不明点: `未確定事項`

次の原則を守る。

- 完了条件は実装方法ではなく、完了を判定できる観測可能な結果として書く。
- ユーザーが指定していない技術、UI、期限、優先度を勝手に決めない。
- リポジトリを読めば分かる情報を未確定事項にせず、先に調査する。
- 本文は日本語で簡潔に書き、曖昧な代名詞や空のチェック項目を残さない。
- ラベルは付与しない。
- assigneeは原則`mitchi-0719`とする。

## Issueを作成する

closed Issueについて確認ありモードでreopenが選ばれた場合は、新規Issueを作らず、既存Issueをopenへ戻す。必要なら、今回の依頼で再対応する理由と追加の完了条件をコメントし、reopenしたIssueのURLを返す。reopenの成否が不明な場合も新規Issueへ切り替えず、現在の状態を再取得してから停止する。

GitHub Appが利用可能なら、それを使ってラベルなしでIssueを作成し、可能なら同じ操作で`mitchi-0719`をassignする。`docs/GITHUB_AUTHENTICATION.md`で定義されたフォールバック条件を満たす場合は、一時ファイルを使ってshell展開を避け、次の形で作成する。

```bash
gh issue create \
  --repo "{owner}/{repo}" \
  --title "{接頭辞}: {短い概要}" \
  --body-file "{安全に作成した一時ファイル}" \
  --assignee "mitchi-0719"
```

- `--label`は指定しない。
- assignee設定だけが失敗した場合、既に作成されたIssueを重複作成しない。Issue URLとassignee失敗を報告する。
- 作成要求がtimeoutなどで不明瞭に終わった場合は、再試行前に同じタイトルと直近のIssueを検索する。作成済みならそのIssueを返す。
- 明確に未作成だと確認できた場合だけ1回再試行する。それでも結果を確定できなければ停止し、成功扱いにしない。

## 完了報告する

作成した場合は次を返す。

- Issueタイトル
- Issue番号とクリック可能なURL
- assignee
- 確認なしモードで置いた仮定と未確定事項
- 関連付けた既存Issue

既存open Issueを再利用した場合は、新規作成していないことと一致理由を明記する。起票できなかった場合は、コピー可能な完成済みタイトル・本文と、失敗した段階、利用できなかったアクセス経路を返す。
